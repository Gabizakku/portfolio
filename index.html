Six systems, in production

01Statement pipeline: ERP export to per-customer statements and mailbox drafts

The problem. Statements were built by hand in four steps, and the dangerous one was matching credit notes. A credit note paired to the wrong invoice produces a statement that looks perfect and is wrong.

What I built. One entry point that reads the ERP export, pairs credit notes reference-first, never amount-first, matches payment slips against a candidate set, checks every customer subtotal against the export total, then emits one workbook and one email draft per customer. Idempotent runs, every artefact named by run.

Proof. Read-back on every draft for count, recipient and total. A checksum per workbook. False positives are struck before a draft exists. Four production runs, the last producing dozens of statements out of hundreds of open rows, all verified on read-back.

Python · openpyxl · IMAP/SMTP · scheduled Windows runs

02Driving a desktop ERP that has no write API

The problem. A native Java ERP client whose REST layer is read-only. The only write path is the interface, on a machine a person is also using. Cursor and screenshot automation would fight the user and break on a window move.

What I built. A bridge into the JVM accessibility tree through Java Access Bridge, reading and invoking components by accessible role and name. No cursor, no screenshots, no focus stealing, running in the background while the machine is in use.

Proof. Every read compared against the read-only REST surface where one exists, every write followed by a re-read of the same field. One long-lived client rather than per-call attaches, because repeated attaches are what make this class of automation flaky.

Python · Java Access Bridge via ctypes · UI Automation fallback · REST verification

03Arrival monitoring across four carrier portals

The problem. Four carrier portals, no API keys, no paid tracking service, and the same question answered differently by each. Somebody had to check the seven-day window every weekday evening.

What I built. Four adapters on one persistent browser session, each returning planned against actual arrival per container, behind a selection pass that decides which shipments are even eligible. Deterministic scraping, not inference.

Proof. The selection pass is tested on ineligible rows, so a shipment outside the window is never reported as an exception. Failures surface as a named portal, not a silent gap.

Python · Chrome DevTools Protocol · scheduled weekday run

04Verification as a habit, not a promise

The problem. Tests that pass while the output is wrong. It happened once, visibly: a suite went green on an implementation a fresh read found six defects in.

What I built. Read-back per artefact, so a draft is created and then re-read field by field. Checksums per file with an audit trail per deletion. Negative tests that assert what must not appear: the false positive, the ineligible row, the duplicate send.

Proof. A 411-file, 47-folder handover shipped with 0 duplicates, 0 missing, 0 extra, 0 checksum mismatches, owner-only access, and every removed file logged with its reason.

Playbook applied to every system on this page

05CRM estate ownership and a two-way CRM sync

What I built. Nine months owning roughly 90% of an agency's workflow estate across live client accounts: pipelines, booking logic, follow-up sequences, notification fan-out. Then a two-way Zoho to CRM sync over n8n and REST webhooks so lead records and pipeline stages stayed aligned without manual reconciliation.

Proof. Conversations and opportunities are traced end to end after every workflow change, and a sync is trusted only after a round trip on a real record.

GoHighLevel · Zoho · n8n · REST webhooks · field and stage mapping

06The operating system around the work

What I built. Solo delivery across several streams with no project manager, so the work needed a spine: a task register with stable IDs that are never reused, claim and close discipline, generated board views, and audit scripts that compare what the register says against what the files show.

Proof. The audit is adversarial. It looks for rows called open that are closed, handoffs claiming work nobody did, and progress computed from mismatched denominators. Two of those were found and corrected.

Python · SQLite · generated reports · adversarial audits

How the work holds up

Read-back, always

Nothing counts as done because a script returned success. It counts when the artefact is read again and compared to what it should say.

Negative tests

The important assertions are about absence: no duplicate send, no ineligible row, no client billed twice.

Small blast radius

Background automation that does not steal focus, does not need a babysitter, and can run on a machine somebody is using.
